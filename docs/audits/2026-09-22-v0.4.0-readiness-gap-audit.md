## B. Tradability correctness

`fetch_tradability()` is conservative and implements the intended order:

```text
calendar → delisting date guard → suspension → verdict
```

The test contract locks all requested high-risk cases:

- calendar failure/unknown never becomes `True` or `False`;
- a partial calendar's positive membership may be used, while negative
  membership remains unknown;
- a confirmed market closure short-circuits delisting and suspension;
- a covered delisting miss continues, BSE/uncovered and own-market failures
  remain unknown, and malformed delist dates remain unknown;
- an effective delist date blocks on the date itself and afterward, while a
  future delisting date does not affect an earlier request;
- suspension uncertainty never produces `tradable=True`.

**Listing-date / IPO eligibility decision: DEFER v0.5+.** The released
contract is a conservative answer built from trading calendar, terminated
listing evidence, and suspension snapshot evidence. `delisting.py` explicitly
defines `eligible_by_delisting` as narrower than listing or full tradability.
No repository consumer requires IPO eligibility, and no existing public
contract promises lifecycle-complete listing status. Adding it now would be a
new lifecycle source and policy surface, not a repair to an asserted result.

## C. PIT and historical correctness

- Daily bars apply the requested inclusive window and canonical date schema;
  cached OHLCV reapplies `Date <= curr_date` after disk ingress and structured
  refresh, before its 800-bar truncation. Tests cover future cache rows,
  malformed cache bypass, stale coverage, and convergence.
- Calendar records the actual final bar date separately as `data_as_of`; local
  stale policy is visible rather than silently treated as current.
- Tradability does not turn a current delisting-list membership into a
  backwards-looking block: it compares requested date with the official
  `delist_date`. The date guard regression tests cover prior, equal, and later
  requests.
- The existing financial historical path uses `point_in_time.filter_financial_records`
  and displays `POINT_IN_TIME_LIMITED_MARKER` when post-analysis-date report
  versions are excluded. No new conflict with the v0.4 structured work was
  found.

The audit does not claim the repository is a complete point-in-time database;
it finds the paths that publicly assert historical/as-of behavior truthful in
their stated scope.

## D. FetchMetadata and provenance

`FetchAttempt` records a single provider observation. `FetchMetadata` keeps
provider-route truth (`final_status`) distinct from engine-declared
request truth (`outcome_status` / `request_status`), with explicit
`providers_used`, single-provider invariant for `final_provider`, `partial`,
`stale`, limitations, and timing fields. Daily-bars tests specifically lock
the "provider succeeded but requested window is empty" case.

The same-day delisting disk-cache path intentionally returns
`attempts=[]`, `request_status=success|normal_empty`, and
`final_status=skipped` / `succeeded=False`: it performed no provider call and
therefore must not invent an attempt or health write. The cache-hit regression
test verifies that behavior; repository consumers do not read `succeeded` or
`final_status` for this result, and the public documentation makes no contrary
cache-success promise.

**Classification: DEFER v0.5+ contract debt, not a blocker.** A future
metadata revision may add an explicit cache-serving state or a separately
named request-completion predicate. Doing so before freeze would reshape a
generic public model without a demonstrated consumer ambiguity. Consumers can
correctly use `request_status` today.

## E. Capability health correctness

The matrix and implementation demonstrate operation-scoped identity for quote,
daily bars and index bars, and the new slices use:

```text
eastmoney:suspension_snapshot
sse:delisting
szse:delisting
```

`tradability` creates no health identity, and cache hits create no synthetic
provider observation. Structured mootdx calls suppress primitive observation
until their canonical boundary classifies the response. `record_fetch_observation`
is the common one-attempt/one-health write mechanism. The isolation tests cover
mootdx method capability separation and structured-vs-primitive duplicate
write prevention. No duplicate health ownership was found.
