# chstockdata v0.4.0 — 设计符合性与 Gate 审计（追溯）

## 1. 结论

**总体：核心技术方向与 v0.4.0 经修订后的设计一致；存在设计追溯/变更控制缺口以及必须由 RH3-A 关闭的真实 consumer qualification 缺口。不能把“Release Hardening Ready / RH2.1 PASS”表述为“v0.4.0 已获最终发布授权”。**

- 未发现由 Phase 1–8 引入、在当前代码/既有审计中已证明的新增 package architecture/correctness blocker。
- Calendar、Suspension、Delisting、Tradability 扩展了最初的 quote/bars P0 内核，但按阶段实施并回归，属于已实施的增量扩展，不是当前必须回滚的越权重构。缺的是总版本设计及正式 scope-change 追踪。
- corporate actions structured 能力虽被早期三仓计划列为重要后续受益点，但截至基准仍为 legacy；不要谎称“所有 consumer 最有价值的能力已完成迁移”。
- **RH3-A consumer canary 尚未验收；两个消费者均有版本/安装约束，不能拿 chstockdata 单仓 657 passed 或 wheel import 来替代。**
- 287 条 full Ruff 存量 findings 已按 RH1 gate 基线化；不因计数本身重开 God Module cleanup。
- RH2.1 release workflow 只经过本地 preflight，实际 GitHub/PyPI operational gate 留在 RH3-B；不创建测试 tag。

## 4. 需要明确标红的 Gate 事实

### F-01 — [PROCESS / CLOSED AS RETROSPECTIVE GAP] 原始版本设计文件缺失

最初三仓路线图有 v1→v2→v3 的重大前提修订，但 Phase 1 动工前本仓库没有独立、可审计的 v0.4.0 version-design.md 及明确 scope-change register。当前阶段测试与 Readiness Audit 不能证明所有前置 gate 当时已以统一版本设计冻结。本次补建是 provenance 修复，**不得将追溯文档描述为 9 月 21 日已冻结的 original gate**。建议 Owner 审核本文件后再决定并入 main。

### F-02 — [HISTORICAL SOURCE IDENTITY / CURRENTLY CLOSED] 早期 v3 使用错误的全 SHA

早期会话 v3 引用 143eb5a3c0e02a95b1c11a2e7c61e8ac470b5f77（当前 GitHub 不存在）。真实 chstockdata v0.3.0 release SHA 为 143eb5a61e11003a4b29461eeb78deec0ab8d8e5；systematic-investing-os 当前 SOURCES.yaml 已修正。留痕，不再据旧 SHA 作当前失败结论。

### F-03 — [DESIGN DEVIATION, NOT AUTO-BLOCKER] 供应链建议变更缺少独立决策记录

原计划 v1 曾建议 Tencent Kline 代替 mootdx；v2 把此要求改成需真实 capability/liveness 证据，v3 的 v0.4 核心也不再强制。实际保留 vipdoc→mootdx→Sina，既有 cache、source label、fallback/单位 regression 支持这个选择。缺少明确记录“为何不采用 Tencent Kline”的版本级决定；若 live evidence 不能证明新链更可靠，不得为了追赶旧建议而改造。记录解释即可，不重开 RH3 功能范围。

### F-04 — [SCOPE / DOCUMENTATION] Corporate actions 与早期 consumer value 有差距

早期 v2 设想 structured corporate actions，v3 将其列为 systematic-investing-os 将来适配的高价值对象；本次六条实现不包括它。0.3.0 legacy ETF/stock company-action 接口仍存在，未被证明是 0.4 package release blocker，但“所有高优先级 consumer 能力已结构化”的说法不成立。独立决定是否 defer v0.5+，不要把此次版更描述为完成所有 consumer migration。

### F-05 — [RH3-A GATE, OPEN] 不能用旧 pin 的 consumer 直接声称候选包可用

systematic-investing-os 当前 main 的 third_party/SOURCES.yaml pin 0.3.0 exact source；其 adapter 的 PINNED_CHSTOCKDATA_VERSION = "0.3.0"，validate_library_version 对其他版本 fail closed。因此 0.4.0 wheel 在原始冻结运行时被拒绝是**预期安全行为**，不是 chstockdata API 回归。RH3-A 必须在隔离副本用明确记录的临时版本资格改动证明真实适配与 golden/requalification，不能改冻结 M0/main pin，亦不能把“我手动跳过版本校验”算 PASS。

TradingAgents-AStock-Private 的 product/v1.0.0 分支 pyproject.toml 在本轮查询时仍有 chstockdata[baostock]>=0.2.0,<0.3 声明；这不能原样解析安装 0.4.0。应先确定 RH3 选用的真实目标分支/lock/shim，再在独立 worktree 标注临时 dependency override 并运行 consumer-specific deterministic tests。不要将当前这份 manifest 直接当作“两个 consumer 均已兼容 0.3/0.4”的证据。

**Release qualification 与 consumer actual adoption 是两个 gate。** 任何本地 consumer canary 通过均不得自动更新下游生产 pin。

### F-06 — [SEMANTIC LIMITATION, DISCLOSED] PIT 与 eligibility 的范围

Phase8 使用 official delist_date 防止 later-delisting 状态污染早期请求，但不是完整 historical availability database；日期早于 IPO/list_date 仍可能被 v1 six-field tradability 视为 true（若其它 covered facts 均清），不能向量化或策略交易方宣传为完整交易资格。BSE delisting 仍 unknown；cache-only metadata.final_status=skipped 但 request_status 可以成功。以上已在 README/MIGRATION/architecture 中有限披露；若 RH3 consumer 要将它作为硬下单/回测 eligibility，则属下游契约 blocker，不能依靠修改文案绕过。

### F-07 — [OPERATIONAL RELEASE GATE, OPEN] GitHub/PyPI 真正发布尚未验证

RH2.1 已有 fetch-depth:0、动态 tag/project/installed metadata/runtime 校验、构建/安装 gate 且 publish.needs:build；但未 push tag、未检验 PyPI Trusted Publisher 的实际 account/environment。不能将本地 YAML preflight 写成 live publishing PASS。RH3-A 只能模拟 RC，RH3-B 必须 Owner 单独授权后执行。

## 5. 对“范围扩大、Gate 没守住”的判定口径

- **没有发现应把 Phase 5–8 回滚的功能越界**：它们是用于补足已有 consumer 数据事实、安全判定而逐步增加的 additive slices；没有引入 GenericRouter/全量代码重写/下游产品域模型。
- **存在版本级治理缺口**：阶段决策和 tests 很强，但在最初未有 version-design.md；初次 Phase2 canonical/volume/metadata 缺口、Phase1 runtime health 隔离、Phase6 partial calendar 均由后续小阶段关闭。这说明阶段 gate 有识别/纠错能力，不等于这些缺口从来没发生，也不能把后验修复反称“首次 gate 就 PASS”。
- **当前真正不得越过的 gate 是 RH3 consumer qualification 和 RH3-B 发布授权**。如果 RH3-A 只是把 0.4 wheel 安装好、完全跳过 consumer version pin，属于 gate failure。若推 v0.4.0 tag 做试验，会触发真实 PyPI workflow，属于跨授权边界。

## 6. 最小后续行动（不启动 Phase 9）

1. 由 Owner 审阅追溯 version-design 与本审计的历史解释，决定接纳为版本设计记录；主分支 RH3 开发不因这两个文档被自动修改。
2. RH3-A 使用真实 0.4.0 RC wheel、两个隔离 consumer 和可归因的 pin override/qualification fixture；记录各自 PASS/FAIL/BLOCKED、旧失败与新回归。
3. 在 RH3-A 文档中明确 corporate actions structured defer 决定、Tencent Kline 路线处置，以及 BSE/listing/PIT 限制是否满足 consumer contract。
4. RC 测试、static gate、build/twine/clean install、发行版本四方一致后，STOP at Owner Review；未授权绝不创建/推送 tag。
5. RH3-B 单独授权后才检查真实 GitHub pypi environment / Trusted Publisher 并执行正式发布。
